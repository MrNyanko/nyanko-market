# 把视频写成能独立阅读的长文

从原片的论证出发。先找到作者起初怎么想、哪一次实验改变了他的判断、最后把判断用在什么选择上。将一个案例在片头、中段和结尾出现的线索串起来。同一个故障可以先由测试发现，再由脚本抓取，最后由另一个程序定位原因。给出相应时间链接，让读者可以回到原画面核对。文章篇幅跟着论证和证据走；整片深读时回看每个主要段落有没有在文章里得到解释。

对演示还原到读者能推理的程度。写清操作在哪个窗口执行、输入和输出各是什么、屏幕上有哪两种状态容易混淆。引用命令时核对参数、引号、管道和条件分支。区分原片执行的命令、便于解释的伪代码、拍摄时的产品状态，以及作者对未来的猜测。优先为文字很难说清的操作配图（例如拖选越界、恢复记录与目标窗格），取读者能看清的停稳帧，图注点出该看哪一处。保留来源署名。上传的只应是用户指定范围内的文章素材。

## Obsidian

优先用可用的 Obsidian CLI 确认 vault 和同类笔记的目录，遵循现有 frontmatter、附件和内部链接习惯。新文章先检查重名；用户要重写就更新原笔记并尽量保留路径。将正文使用的图片写入 vault，用可解析的相对路径引用，在应用内回读正文并核对每个图片链接。特别检查 shell 代码中的反斜线和换行。命令行传参应保留原文，避免由 shell 二次解释。没有可用 CLI 时，已知并获准写入的本地 vault 也可直接保存 Markdown 与附件。

## Notion

已指定目标页就按该位置创建或更新；只说“给我看看”时采用私人页面。优先用已连接的 Notion 工具，把长文排成标题、可跳转目录、图片、代码块和对照表。产品名或作者历史观点依原料保留，每张图使用实际可上传的文件。跨平台复制时把 Obsidian 双链换成目标里真实存在的链接，或删去平台内导航。

连接不可用时，可以用用户已登录的桌面端导入。无可用写入途径就交付可导入 ZIP（根层一篇 Markdown，附件用相对路径）并说明云端状态；之后连接可用时，先检查是否已经导入，避免重复建页。完成后打开实际目标页，核对图片数、代码段、时间链接、目录以及导入后可能重复的标题，交付正文链接。
